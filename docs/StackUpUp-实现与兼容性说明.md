# StackUpUp 兼容性说明

本文是面向玩家和整合包作者的简版说明，只回答三个问题：

1. 它为什么比旧方案更适合 1.12.2 整合包。
2. 它大概能兼容哪些情况。
3. 什么时候仍然可能需要额外补丁。

## 1. 它现在重点解决什么

StackUpUp 当前最重要的改进，不是“把数字改大”，而是把规则匹配的视角尽量提升到更接近真实 `ItemStack` 的层面。

这意味着它更擅长处理：

1. 同一物品 ID、不同 `metadata` 的子物品。
2. 需要按矿物辞典统一处理的一整类材料。
3. 需要让规则在大型整合包里保持更可读、更好维护的情况。

## 2. 为什么这很重要

在 1.12.2 里，很多大型模组都会把大量子物品挂在同一个物品 ID 下面，再用 `metadata` 区分具体内容。

GregTech CEu 就是最典型的例子：

1. 钢锭、钢板、钢粉等很多内容并不是完全不同的物品 ID。
2. 它们经常共享同一个物品对象，只靠 `metadata` 区分。

如果规则系统只能停留在“按物品 ID 粗略匹配”，那么这些物品很容易一起被误伤，或者根本无法单独设定。

## 3. 现在的兼容思路

StackUpUp 追求的是更上层的统一兼容：

1. 优先修补原版公共路径上的堆叠限制。
2. 优先让规则系统自己表达 `item + meta + ore` 这些真实需求。
3. 只在确实有必要时，才对特殊模组路径补兼容点。

这样做的好处是：

1. 不需要为了每个模组都写一整套独立规则。
2. 同一套 DSL 可以覆盖更多 1.12.2 常见场景。
3. 后续继续迁移时，维护成本更低。

## 4. 哪些情况通常能工作

1. 只要物品最终还是走常规堆叠语义，通常都能通过规则命中。
2. 同 ID、不同 `metadata` 的物品，现在已经进入主要兼容与回归范围。
3. 按矿物辞典统一调整钢锭、铁锭、粉、板一类材料，也更自然。

## 5. 哪些情况仍可能出问题

1. 某些模组自己在容器、网络或终端逻辑里额外写死了 `64`。
2. 某些交互不是普通拿取/放入，而是它们自己的特殊点击逻辑。
3. 某些物品本身就不适合大堆叠，比如强依赖独立 NBT 的物品。

遇到这些情况时，通常不是规则文件写错，而是那个模组还有额外限制路径没被覆盖。

## 6. 对玩家来说怎么判断是否值得用

如果你的整合包里：

1. 有大量材料类物品想统一改堆叠。
2. 有很多同 ID、不同 `metadata` 的老模组物品。
3. 不想为了改堆叠再引入一整套很重的脚本体系。

那么 StackUpUp 就是值得优先尝试的方案。

如果你遇到的是某个模组自己额外写死的特殊终端、特殊容器或特殊交互，再考虑继续补兼容。
