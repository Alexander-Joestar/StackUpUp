- CleanMix 0.7.1 的 obfuscation AP 已加入 annotation processor；`compileJava` 生成 `build/tmp/mixins/mixins.StackUpUp.refmap.json`，processResources 后的 refmap 与其一致，并包含 SRG 映射。证据与命令结果见 `docs/agent/compatibility-decision-record.md` §8.6.1「refmap 修复实施记录」段。
- 11.13 dev 服务端日志已出现 CleanMix/MixinExtras 初始化、`Successfully loaded Mixin Connector`、early 配置准备与 refmap remap；connector 的模块表再按 mod presence 与 `MixinToggles` 加载 late 配置。证据见 CDR §8.6.1、§8.8。
- 11.13 迁移后的 `test`、三项字节码护栏和编译检查有通过记录；最近一次矩阵通过（2026-08-10，`run/logs/autotest-report.txt`，最终状态 PASS），此后代码改动未经矩阵重跑，故不能把迁移写成 T14.7 通过。预存探针语义与迁移装载证据见 `docs/agent/compatibility-decision-record.md` §8.8，转发 wrapper 探针预期修正见同文件 §3.12。
- 10.7 的双端 provider、初始化和 refmap 日志仅作历史对照；历史 JSONL 守恒报告也仅作历史产物，方案 A 已归档，当前不生成 JSONL，不以其作为 T12/T13 解锁条件。

## 3. UNKNOWN 与缺口

1. 生产混淆（notch 命名）环境消费 refmap 尚未实测；dev/SRG 装载证据不能替代该验证。
2. 第三方 mod jar 与真实写入源码缺失时统一为 **无源码不可判定**，不能据 connector 命中或类名证明容量安全；台账见 CDR §5.4。
3. CleanMix/Extras 的部分运行时与双 ASM 细节虽有 jar/AP 证据，仍需按 T14.7 要求由独立复核确认；高风险 Mixin 行为不因 provider 初始化成功而闭合。
4. 自动化实现已将矩阵目标异常隔离、未知 probe ID 和链接异常归入失败路径；本审计 lane 未重新运行矩阵，不能把该行为或完整矩阵写成通过。
