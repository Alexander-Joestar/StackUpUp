## 0. 结论摘要

1. **配置分层现状**：13 个 JSON（early 1 + late 12）与两个 loader 双向 13/13 对齐，无未注册项（t14.1 §1/§5.1 一致，Q-UNREG 无）。early = core 层（required 缺省 true，20 注册项）；late 12 个 = optional 层（6 个 `required:false`，6 个无 required 键 → 缺省 true，见 §1 表）。
2. **require 现状**：显式 `require=0` 共 **22 处**（Q-REQ0-01~22，与 t14.1 §5.3 逐条对应，源码行号已核，§6.1）；全仓无 `@Expect`；无显式 `require>0`。
3. **关键新证据（字节码）**：mixinbooter-10.7.jar 内嵌 Mixin 核心（0.8.7 fork）中，**注入注解缺省 `require` 的 requiredCallbackCount = 0**（`MixinConfig.getDefaultRequiredInjections()` 恒读 `injectorOptions.defaultRequireValue`，构造为 0，与配置级 `required` 无关）。因此 **early 核心 27 处无显式 require 的注入点同样默认静默**——「核心注入 fail-fast」现状**不成立**；目标类缺失（非 pseudo）仅 WARN 不崩溃（除非 strict）；崩溃路径仅限 minVersion/feature 不满足（required 配置）、显式 require>0 注入点缺失、target 加载过早。
4. **optional 缺失日志现状**：mod 缺失/toggle 关闭 → loader 跳过**零日志**（LoadControllerMixin 字节码确认）；注入点缺失（require=0/缺省）→ **零日志**；@Pseudo 目标缺失 → DEBUG 级（默认不可见）。「optional 缺失无日志即成功」现状成立，**命中 T14.5 停止条件**。
5. **配置未注册检测**：当前无任何自动检测机制；`StackUpUpLateMixinLoader.kt:12` 的 `?: return true` 是「未知配置无条件入队」的结构面（当前无违规项，未来新增 JSON 忘登记时会静默全量装载）。
6. **勘误（相对 t14.1 OBS-02）**：「SimpleInventoryMixin 无 require → 默认 require=1、Q-DUP-01 硬失败面」在本运行时（10.7 内嵌 0.8.7）**不成立**——缺省 requiredCallbackCount=0，Q-DUP-01/02 双配置上下文均静默。风险面从「硬失败」修正为「双 JSON 装载 + 静默失效」（UNKNOWN 面不变，§6.2）。

## 2. 失败诊断现状（任务第 2 项）

### 2.1 核心注入是否 fail-fast —— **现状：否**（命中 T14.5 停止条件）

字节码证据（mixinbooter-10.7.jar 内嵌 org/spongepowered/asm/*，2025-01-08 构建，运行日志确认运行时唯一 Mixin 核心）：

- `InjectionInfo.<init>`：`requiredCallbackCount=0`（putfield offset 75-76）、`expectedCallbackCount=1`（offset 70-71）、`maxCallbackCount=Integer.MAX_VALUE`（offset 79-82）。
- `InjectionInfo.parseRequirements`：注解无 `require`（或 ≤ -1）且 group 为 default → `requiredCallbackCount = MixinTargetContext.getDefaultRequiredInjections()` → `MixinConfig.getDefaultRequiredInjections()` → **`injectorOptions.defaultRequireValue` = 0**（`MixinConfig$InjectorOptions.<init>` iconst_0 putfield；MixinConfig 中无任何 putfield defaultRequireValue 的其它写点，也无 "injectors"/"defaultRequire" JSON 键字符串）→ **配置级 `required=true` 不抬高注入默认值**。
- `InjectionInfo.validate`：`injectedCallbackCount < requiredCallbackCount`（0<0 恒假）→ 缺失注入点**零日志、零异常**；仅 `require>0` 时抛 `InjectionError("Critical injection failure: ...")`。
- `MixinInfo.handleTargetError`：仅 `strict` 字段（mixin.debug.strict / config strict）→ error+throw InvalidMixinException；非 strict：soft=false → WARN 级 `@Mixin target %s was not found %s`；soft=true 且非 verbose → DEBUG 级（默认不可见）。
- `MixinInfo.readTargetClasses`：目标类缺失 → `isVirtual()`（@Pseudo）→ DEBUG `Skipping virtual target {} for {}`；非 virtual → handleTargetError(soft=false) → WARN，**不崩溃**。
- `MixinConfig` 崩溃路径（required 配置）：minVersion/requiredFeatures 不满足 → WARN + `MixinInitialisationError("Required mixin config ... requires ...")`（字节码确认；early.json:5-6 minVersion 0.8 满足，当前不触发）。

推论：early 核心 27 处无显式 require 的注入点（t14.2 E01~E28 减 Q-REQ0-01）与 Q-REQ0-01 一样在注入点层面**静默失效**；核心「fail-fast」仅剩三条窄路径（版本不满足 / require>0 / target 过早加载），均未在本项目配置中启用。**这直接违反 T14.5 禁止项「不得用 require=0、required=false 或 @Pseudo 隐藏核心目标缺失」的意图面**（early 未显式声明 require=1）。

### 2.2 optional 缺失是否有日志 —— **现状：无日志即成功**（命中停止条件）

- loader 级跳过（mod 缺失 / toggle=false）：`zone/rong/mixinbooter/mixin/LoadControllerMixin.class` 字节码——`shouldMixinConfigQueue` 返回 false 时**不产生任何日志**；仅 true 时 INFO `Adding [%s] mixin configuration.`。运行日志实证：run/logs/latest.log:59-60（early loader + Adding early）、:1054（`Loading late loader [io.alexjoest.stackupup.bootstrap.StackUpUpLateMixinLoader] for its mixins.`）——**12 个 late 配置全部跳过且零日志**（无第三方 mod 环境）；SERVER 日志（run/logs/2026-08-08-1.log.gz）同构。
- 注入点缺失（require=0 或缺省 0）：零日志（§2.1）。
- @Pseudo 目标缺失：DEBUG 级（默认不可见）。
- 全仓无 mixin 配置/目标状态的机器报告设施（rg 无 machineReport/missingTarget/configReport 命中）；ConservationAuditor（T12.3）只覆盖守恒事件，DevAutomation 探针覆盖部分兼容失败但不覆盖 mixin 装载状态。

### 2.3 配置未注册是否有检测 —— **现状：无检测**

- 当前无违规（JSON↔loader 13/13 对齐，t14.1 §5.1 Q-UNREG 无）；但无任何启动期双向校验代码。
- `StackUpUpLateMixinLoader.kt:12` `modules.firstOrNull { ... } ?: return true`：**不在 modules 表的配置会被无条件入队**（绕过 isModPresent 与 toggle 检查）——未来新增 JSON 忘登记时的静默全量装载面。
- JSON 文件缺失时的 MixinBooter/Mixin 行为未运行验证（UNKNOWN）。

## 3. 目标缺失日志/机器报告契约建议（只建议，不实施）

1. **分层声明**：early 配置 = core 层（装载必须 fail-fast）；late 12 配置 = optional 层（允许缺失但必须有日志+机器报告）。
2. **core fail-fast 门**：early 配置建议显式 `required:true` + 注入注解显式 `require=1`（或等价 strict 校验）；任何核心目标/注入点缺失 → ERROR + 启动中止（含可关闭开关，如 `-Dstackupup.core.failFast=false`，关闭态必须显式 WARN 并写入机器报告）。
3. **optional 缺失日志契约（建议字段）**：`configName`、`modId`、`targetClass`、`injectionPoint(owner/name/descriptor)`、`requireValue`、`resolution(APPLIED|SKIPPED_MOD_ABSENT|SKIPPED_TOGGLE_OFF|TARGET_MISSING|INJECTION_MISSING)`、`timestamp`、`side(CLIENT|SERVER)`。级别：TARGET_MISSING/INJECTION_MISSING 至少 WARN（当前 DEBUG/无日志）；MOD_ABSENT/TOGGLE_OFF 至少 INFO。
4. **机器报告**：启动期一次性输出（建议 `config/stackupup/mixin-report.json` 或等价路径），供 T14.7 自动化验收断言；字段与上表一致，逐配置逐注入点一行。
5. **配置未注册检测**：loader 启动期校验 `getMixinConfigs()` 返回值 ↔ JSON 资源存在性 ↔ modules 表双向对齐；不一致 → ERROR + 机器报告 +（core 层）中止。
6. **报告落点责任**：建议由 bootstrap 层（StackUpUpCore/StackUpUpLateMixinLoader 同级）统一收集，不散入各 Mixin handler；不改任何现有日志断言。
7. **与 T12.5/T14.3 关系**：H1 组（E06/E13/E16/E17/E18/E19，t14.3 §5）行为测试门先行；本契约不替代行为测试，只保证「缺失可定位」。

## 5. 10.7 → 11.x 加载路径差异（引用 t14.4）

- 基线：`gradle/libs.versions.toml:20` mixinbooter=10.7；`build.gradle.kts:53` modUtils.enableMixins 字符串坐标；t14.4 §1 运行闭合：唯一 provider = mixinbooter-10.7.jar 内嵌（Mixin 0.8.7 + MixinExtras 0.5.0，双端运行日志）。

- 对本项目 loader 的影响面（引用 t14.4，全部 UNKNOWN 未运行验证）：①`IEarlyMixinLoader`/`ILateMixinLoader`/`Context.isModPresent` API 在 11.x 的可用性与语义（AGENTS.md 明示「若上游 11.x 已改变或淡化 early/late 机制，不得把旧规则无条件套用」）；②11.x 下注入缺省 require 语义（CleanMix 0.7.1 的 defaultRequire 规则可能不同于 10.7 内嵌 fork，需 11.x 源码+运行日志闭合）；③本项目 13 个 JSON 的 `target:"@env(DEFAULT)"` 与 11.x init.json `@env(PREINIT)` 的关系；④refmap 生成路径（CleanMix 自带 AP）无运行证据（t14.4 §4）；⑤双 ASM/CoremodClassFilter 对 com/llamalad7 类的覆盖（t14.4 §6 沿用 8.7 ④⑥）。
- 结论：10.7→11.x 全部运行行为维持 **UNKNOWN**（t14.4 UNKNOWN-A/B/C）；本审计的「缺省 require=0」「loader 跳过零日志」结论仅对 10.7 成立，迁移后必须按 11.x 实际行为重建（T14.7 把关，本审计不实施迁移）。

### 12.1 验证方法（JUnit 环境真实应用 mixin）

探针在 JUnit 环境内**真实加载 MixinBooter 10.7 内嵌 Mixin 核心（0.8.7 fork）并走完整应用链**（config 匹配 → MixinInfo → MixinTargetContext → InjectionInfo → inject），不是结构检查。已确认的普通 JVM 预条件（每一条都是运行中实测出来的阻塞点）：

1. **LaunchWrapper 服务可用**：测试 classpath 含 launchwrapper 1.12，`MixinServiceLaunchWrapper.isValid()` 只读 `Launch.classLoader` 静态字段（普通 JVM 返回 true）。
2. **`Launch.classLoader` 必须能解析测试 classpath**：mixin 核心经 `Launch.classLoader.getClassBytes/getResourceAsStream` 读配置 JSON 与类字节；初版传空 `LaunchClassLoader` 导致 `IllegalArgumentException: The specified resource ... could not be read`。改为喂入 `java.class.path` 全部 URL。
3. **排除 mixinbooter jar 自身出 sources**：其 manifest `MixinConfigs` 属性会被 Mixin 平台代理注册为 `mixin.mixinbooter.init.json`（CrashReportMixin/LoadControllerMixin），普通 JVM 下 PREPARE 必 NPE（`Mixin prepare for mod unknown-owner failed preparing CrashReportMixin ... NullPointerException`）。排除后该配置不再进入平台容器，mixinbooter 类仍由父 classloader 加载。
4. **`Launch.blackboard` 必须补 HashMap**：Mixin 核心 `Blackboard`（IGlobalPropertyService）直接读 `Launch.blackboard` 静态字段，普通 JVM 为 null → `NPE at Blackboard.getProperty`。
5. **阶段对齐**：`Mixins.addConfiguration(String)` 把配置注册到 `MixinEnvironment.getDefaultEnvironment()`（DEFAULT 阶段），而 bootstrap 后当前环境是 PREINIT——transform 必须用 `getDefaultEnvironment()` 驱动，否则配置永不选中（实测「Checking for additional mixins for MixinEnvironment[PREINIT]」后零选中）。
6. **配置必须在首次 transform 前全部注册**：`MixinProcessor.select` 门控为「新环境 或（getUnvisitedCount()>0 且 transformedCount==0）」，首次 transform 后中途新增配置不会被本次会话拾取（实测 arm1 零日志、applied=false）。
7. **mixin 包与目标类分离**：目标类不得位于配置的 mixin package 内（`IllegalClassLoadError: ... is in a defined mixin package ... and cannot be referenced directly`）。

三臂设计：arm0 正向对照（@Inject 到**存在**方法、require=1，证明整条链真实生效）→ arm1（@Inject 到**不存在**方法、**缺省 require**，复现全仓 27 处缺省 + 22 处显式 0 的静默面）→ arm2（@Inject 到**不存在**方法、**require=1**，验证可定位错误机制是否存在）。

证据落盘 `build/neg-probe-evidence.log`（构建产物目录，验证后删除）；`mixin` logger（log4j2，`LoggerAdapterLog4j2`）以 DEBUG 级别挂内存 appender 捕获（与 `StackUpUpLateMixinLoaderSkipLogTest` 同款 CollectingAppender 思路）。

### 12.3 结论（停止条件 4 状态更新）

1. **缺省/显式 require=0 的注入点缺失：完全静默，运行证实**。全仓 early 27 处无显式 require + Q-REQ0-01 显式 0 均属此静默面；10.7 下该行为是 Mixin 核心缺省语义（`defaultRequireValue=0`），loader 层无法在注入点层改变。**10.7 行为边界：无 fail-fast、无日志**——这正是 T14.5 停止条件 4 的「缺省 require=0 掩盖核心错误」。
2. **可定位错误机制存在且运行证实**：显式 `require=1` 的注入点缺失产生 **WARN 级、点名到方法/目标类/失败阶段的可定位日志**（`Critical injection failure: @Inject annotation on ... could not find any targets matching '...' in ... [-> Parse -> -> Validate Targets]`），但不崩溃、不向 transform 调用方传播（`thrown=null`、`applied=true`）。T14.5 §3-2「核心注入点显式 require=1」建议的运行依据成立：能关闭「完全静默」，但形式是「WARN + 继续」而非进程中止（进程中止需 MixinBooter 上游行为或额外门，见 §11.4-1）。
3. **停止条件 4 状态：部分关闭（10.7 边界，如实标注）**：
   - 关闭面：注入点缺失**不再必然静默**——显式 require≥1 提供 WARN 级可定位日志（已运行证实）；T14.5 §3-2 的显式 require 收敛路径有据可依。
   - 未关闭面：缺省 require=0（全仓 27 处缺省 + 22 处显式 0，T14.5 红线不改注解语义）在 10.7 下依然完全静默；在显式 require 决策落地前，停止条件 4 的「掩盖」面仍然成立。
   - **仅对 10.7 成立**：MixinBooter 11（CleanMix 0.7.1）迁移后，注入缺省 require 语义与注入校验行为可能不同（t14.4 UNKNOWN-A/B/C），必须以 11.x 实际运行行为重新验证本节结论；本节不作为 11.x 的依据。
