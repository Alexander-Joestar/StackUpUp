### 6.3 阻塞根因与机制定位

- **根因**：会话锁定（LockApp 持前台）。锁屏状态下：(a) 系统级注入（keybd_event/SendKeys/Robot）投递到锁屏窗口；(b) 锁屏前台不可被普通进程抢占（`SetForegroundWindow`/`AppActivate` 均无效）；(c) 唯一剩余的直投通道（PostMessage/SendMessage 到游戏窗口）消息虽被处理，但 LWJGL2 未将无焦点窗口的键消息转发为游戏键盘事件。
- **LWJGL2 机制（本地证据）**：`lwjgl-2.9.4-nightly-20150209-sources.jar`（Gradle 缓存）中 `org/lwjgl/opengl/WindowsKeyboard.java` 证实键盘事件由 native WndProc 调用 `handleKey()` 事件驱动（Java 侧无焦点过滤），且 `releaseAll()` 注释明确「窗口失焦时释放全部按下的键」——native 侧存在焦点跟踪。native WndProc 是否按 `GetFocus` 过滤：本地无 native 源码（GitHub raw 404×2、API 限流），标记 **UNKNOWN**；实证结果（消息被处理而无键事件）与「native 侧焦点门控」一致。

### 8.3 根因一（代码级，非推测）：1.12.2 的 F3+T 在主菜单/任何 GuiScreen 下是 no-op

对本地已映射补丁类 `build/classes/java/patchedMc/net/minecraft/client/Minecraft.class` 做 `javap -c -p`（jbr-25.0.4）：

- `runTickKeyboard()` 中 F3+T 分支（偏移 175–206）位于 `aload_0; getfield currentScreen; ifnonnull 253`（偏移 177–181）之后——**`currentScreen != null` 时整个 F3 处理块被跳过**。主菜单 `GuiMainMenu`、暂停菜单 `GuiIngameMenu` 都算 `currentScreen != null`，此时 F3+T 不执行。
- `processKeyF3(I)` 全类唯一调用点：`runTickKeyboard` 偏移 203（即上述被 currentScreen 门控的块内）。
- `refreshResources()` 全类唯一调用点：`processKeyF3` 偏移 626（key 20='T' 分支：`bipush 20; if_icmpne 631; ... invokevirtual refreshResources`）。
- 结论：**本构建（1.12.2 + Forge 14.23.5.2847）中 F3+T 只在不处于任何界面时（世界中、未暂停）生效**。本任务此前所有注入（含上一轮方案）都在主菜单执行，按代码必然无效——这与「键未达游戏」是两个独立原因，后者同样被实证（见 8.2 #5/#8）。

### 8.4 根因二（实证）：游戏窗口无法被程序化授予键盘焦点

- `SetForegroundWindow` 返回 True 且 `GetForegroundWindow` 变为游戏窗口，但 `AttachThreadInput` 后的 `GetFocus()` 恒不等于游戏窗口（前台≠键盘焦点）。
- `AttachThreadInput(my, gameTid)` 后直接 `SetFocus(gameHwnd)` 返回 0（失败）。
- 真实鼠标点击标题栏（SetCursorPos+mouse_event，r9 共 17 次）与最小化-恢复循环（17 次）均无法把焦点给到游戏窗口。
- 输入流本身正常：WH_KEYBOARD_LL 钩子确认注入事件进入系统流（8.2 #7），但被送往真正持焦点的窗口；本桌面对注入的接收呈间歇性（8.2 #6，09:41 失败、09:43 成功）。
