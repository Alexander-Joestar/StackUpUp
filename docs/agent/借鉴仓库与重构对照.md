## 1. StackUp：可借鉴的数据流与不可迁移边界

### 1.1 源码数据流

```text
Forge coremod discovery
  → StackUpCore (IFMLLoadingPlugin)
  → StackUpTransformer (IClassTransformer)
  → method-name / class-kind selection
      ├─ MaxStackConstantPatch: BIPUSH 64 → StackUpHelpers.getMaxStackSize()
      ├─ whole-method / helper splice
      ├─ ItemStack count and packet splices
      └─ rendering / creative / inventory compatibility patches

config + registry lifecycle
  → StackUp.preInit(): read Configuration, create config/stackup
  → postInit/register event: reload()
  → ScriptHandler: recursively enumerate files in natural order
  → ScriptContext: line/token matching over the complete Item registry
  → per-Item map: set/add/subtract/multiply/divide
  → Item#setMaxStackSize(target)
  → ASM replaces selected 64 constants and rewrites packet/count paths
```

### 1.2 可借鉴点

1. **旧 Forge 入口的职责边界清晰。** `StackUpCore` 只向 FML 注册 `StackUpTransformer`，并在 `injectData` 设置 coremod
   active：`C:/dev/mc/_tmp/StackUp/src/main/java/pl/asie/stackup/StackUpCore.java:22-53`。这种“加载入口只负责装载，不承载规则业务”的方向可迁移到
   StackUpUp 的 `StackUpUpCore`，但不能迁移其 ASM 选择规则。
2. **确定性文件顺序。** `ScriptHandler.processDirectory` 使用 `TreeSet` 递归处理目录：`.../ScriptHandler.java:48-69`
   。StackUpUp 可以借鉴“输入发现顺序必须显式、可复核”的原则，但应使用 `RuleSourceLocator.resolveLoadOrder()`
   和解析/编译流水线，不恢复直接遍历注册表并改写 live `Item` 的模型。
3. **重载前恢复旧值。** `StackUp.reload` 先恢复 `oldStackValues`，再重新处理脚本：`.../StackUp.java:152-168`
   。可迁移的只是“重载要有明确旧状态处理和报告”；StackUpUp 的目标应是编译新快照、验证后原子替换，不把 live
   `Item#setMaxStackSize` 当作运行态数据库。
4. **向后兼容的数量编码形状。** `PacketBufferWriterSplice` 与 `PacketUtilWriterSplice` 保持非负数量 `0..64`
   的单字节编码，超出该范围后写 magic byte + int：`.../PacketBufferWriterSplice.java:36-76`、
   `.../PacketUtilWriterSplice.java:28-49`。这个“旧包尽量保持兼容、扩展数量有明确标记”的思路可借鉴，但 StackUpUp
   必须增加版本、能力、最大值/编码范围协商；仅复制 magic byte 不是协议兼容证明。
5. **对失败目标记录实际修改结果。** `ScriptContext.applyChanges` 设置后重新读取并警告目标值未生效：
   `.../ScriptContext.java:192-208`。可迁移“结果必须可观察”的原则；审计不能把警告替换成写入后补偿。

### 1.3 明确不能照搬的部分

1. **全局 `Item` 上限不是动态 `ItemStack` 规则。** `ScriptContext` 将匹配结果写入 `TObjectIntMap<Item>`，随后直接
   `Item#setMaxStackSize`：`.../ScriptContext.java:137-173,192-208`。这无法表达同一 `Item` 因 metadata、矿辞、material、tab 或
   NBT 上下文不同而有不同上限，也无法形成 StackUpUp 所需的 `StackContext` 缓存键。
2. **规则解析是即时、可变、局部失败。** `ScriptContext.execute` 捕获 `IOException | TokenException` 后 `printStackTrace`
   ，仍记录已解析行并继续 `applyChanges`：`.../ScriptContext.java:54-72`。StackUpUp 不得将部分解析结果伪装成完整快照；解析/编译错误要带来源、行列和
   fail-fast/旧快照策略。
3. **按接口继承关系和类名扩大容量。** `StackUpTransformer` 对 `IInventory`、`IItemHandler`、`Slot` 的实现/继承关系选择
   patch，并按方法名排队：`.../StackUpTransformer.java:60-116`。这不能证明目标的 setter、`insertItem`、remainder 或 delegate
   写入链能够承载大堆叠。
4. **`BIPUSH 64` 是字节码常量命中，不是容量来源证明。** `MaxStackConstantPatch` 只扫描指定方法，看到 `BIPUSH` 操作数 64
   就替换成全局方法调用：`.../MaxStackConstantPatch.java:39-69`。同一常量可能是协议、显示、单件槽或真实写入限制；StackUpUp
   必须先登记 owner/name/完整 descriptor/真实写入语义，再决定 Mixin 或 ASM。
5. **整方法 splice 的 blast radius 过大。** `StackUpTransformer.spliceClasses` 按方法名匹配并替换整段 `MethodNode`
   ，旧方法改名保存：`.../StackUpTransformer.java:154-219`。这会依赖目标方法结构、继承关系和映射，不能作为 StackUpUp
   新兼容的默认手段；窄范围 ASM 只能在 Mixin 无法表达且写入证据闭合时兜底。
6. **资源定位不能照搬两段 split。** `TokenResourceLocation.apply` 对两边都 `split(":")`，仅接受长度 2：
   `.../TokenResourceLocation.java:31-51`。1.12.2 `ResourceLocation` 的 path 可以含多个冒号；StackUpUp 必须按已核对
   grammar 和源码处理，不按冒号数猜 meta。
7. **没有第三方写入闭环。** 本次核对的 StackUp core/ASM/packet 路径没有 `insertItem` 返回值、`setStackInSlot` 或第三方
   wrapper 的完整写入证据。因此不能把 StackUp 的兼容类扫描写成 Forge 1.12.2 容量安全证明。
8. **没有握手、能力协商或规则同步证据。** magic byte + int 只说明单个编码器的读写对称；没有版本协商、客户端能力确认、配置
   hash 或规则快照同步。StackUpUp 不能在此基础上直接向不同版本/不同模组栈发送扩展数量。
9. **没有 tests/CI/自动验收证据。** 参考仓库本次核对没有可作为 StackUpUp 守恒门的测试和自动化矩阵；“能变换字节码”不能替代真实写入行为测试。

## 2. biggerstacks-Unofficial：可借鉴的数据流与不可迁移边界

### 2.1 源码数据流

```text
server start
  → ServerLifecycleHandler
  → ConfigLib.readRuleset(RULESET_FILE)
  → StackSizeRules.setRuleSet(ruleSet)
  → ConfigFileWatcher
  → on update: replace server ruleset + send ClientboundRulesUpdatePacket

client connection
  → RulesetSyncTask during configuration/login
  → ClientboundRulesHandshakePacket
  → RuleSet.toBytes()/fromBytes()
  → PacketHandler.handleHandshake/update
  → StackSizeRules.setRuleSet(packet.rules())

stack limit query
  → ItemMixin / ItemStackMixin
  → ItemStackSizeHelper.applyStackSizeToItem
      ├─ TemplateOverrideConfig.resolveOverride(ItemStack)
      └─ RuleSet.determineStackSizeForItem(ItemProperties + tag accessor)
  → clamp
  → slot/container/handler/compat Mixin or TransformerLib/XML path
  → tooltip / count display
```

### 2.2 可借鉴点

1. **服务端加载、watcher、广播形成完整生命周期形状。** `ServerLifecycleHandler` 在构造时读取规则并启动
   watcher，在更新时先替换规则再广播，停服时停止 watcher：
   `C:/dev/mc/_tmp/biggerstacks-Unofficial/src/main/java/portb/biggerstacks/event/ServerLifecycleHandler.java:22-68`
   。StackUpUp 可借鉴 watcher 的生命周期收口和“更新事件必须显式发布”的结构。
2. **登录握手与运行期更新分开。** `RulesetSyncTask` 在 configuration 阶段发送当前 `RuleSet`：
   `.../RulesetSyncTask.java:20-43`；handshake/update packet 分别在 `.../ClientboundRulesHandshakePacket.java:18-49`、
   `.../ClientboundRulesUpdatePacket.java:17-43` 序列化 `RuleSet`；`PacketHandler` 在客户端安装两种快照：
   `.../PacketHandler.java:31-63`。StackUpUp 可借鉴“登录前先有规则、运行期更新用同一数据形状”的协议分层。
3. **以 `ItemStack` 为求值入口。** `ItemStackSizeHelper` 从当前栈取得 registry id、namespace、标签、物品类型和原始基线，交给
   `RuleSet`：`.../ItemStackSizeHelper.java:31-77,92-100`。StackUpUp 已有更严格的 `StackContextResolver`/`StackContext`
   ，应继续沿上下文求值，而不是回到全局 `Item`。
4. **模板覆盖提供明确的 item/tag 优先入口。** `TemplateOverrideConfig` 将 item 与 tag 建立查找表，并提供
   `resolveOverride(ItemStack)`：`.../TemplateOverrideConfig.java:113-181,310-336`
   。可借鉴“覆盖规则必须是可枚举、可缓存、可测试的匹配层”，但必须把有效覆盖纳入同一个权威规则快照。
5. **按 mod gating 拆分兼容配置。** `biggerstacks.mixins.json` 有统一清单和 plugin：`.../biggerstacks.mixins.json:1-27`；
   `TransformerEngine.shouldApplyMixin` 按包名提取 mod id 并检查加载列表：`.../TransformerEngine.java:111-147`。StackUpUp
   的 late loader 也应保持每个兼容模组独立、按 `isModPresent` 与开关排队。
6. **明确区分规则传输和能力协议的机会。** `PacketHandler` 注册 `PROTOCOL_VERSION = "1"` 的 configuration/play payload：
   `.../PacketHandler.java:20-52`。可借鉴协议入口，但不能假定一个字符串版本就足够描述扩展数量 codec、快照 schema、最大值和客户端能力。

### 2.3 明确不能照搬的部分

1. **`RuleSet` 同步不等于所有有效覆盖同步。** `ItemStackSizeHelper` 先调用独立的 `TemplateOverrideConfig.resolveOverride`
   ，再查询 `StackSizeRules.getRuleSet()`：`.../ItemStackSizeHelper.java:31-43`；覆盖文件和缓存由 `TemplateOverrideConfig`
   自己读取，路径是规则文件旁的 `biggerstacks-template-overrides.json`，且有独立 `ITEM_OVERRIDES`/`TAG_OVERRIDES`：
   `.../TemplateOverrideConfig.java:84-181`。handshake/update packet 只携带 `RuleSet`
   ，没有该覆盖配置。因此服务端覆盖与客户端覆盖可能不同步。StackUpUp 必须规定： **所有会影响上限的规则、模板、tag/item
   override、preset 和 active cap 都进入同一权威 `RuleSnapshot` 或同一可验证的快照包**。
2. **客户端本地 fallback 会制造权威性分叉。** `ClientEvents.loadRulesetOnLogin` 对远端连接仍尝试读取本地规则，异常时将
   ruleset 置 null：`.../ClientEvents.java:57-79`。StackUpUp 的客户端只能使用服务端协商并验证过的快照；本地文件不得覆盖远端权威快照。
3. **`scaleSlotLimit` 只按原槽位和全局值缩放。** `StackSizeHelper.scaleSlotLimit` 使用 `original`、全局
   `getMaxStackSize()` 和 baseline，特殊处理 `original == 1`，但不读取当前 `ItemStack`：`.../StackSizeHelper.java:15-45`
   。该算法不能证明 item-aware 容量，也不能证明目标真实 setter/insert 路径承载结果。它只能作为“显示/传输速率缩放是独立语义”的反例，不能迁移成
   StackUpUp 容量广告规则。
4. **`CompactingUpgradeWrapperMixin` 没有形成完整的真实插入闭环。** 源码直接调用
   `inventoryHandler.insertItem(resultCopy, false)`，但没有接收其返回值：`.../CompactingUpgradeWrapperMixin.java:64-70`。
   `InventoryHelper.extractFromInventory` / `insertIntoInventory` 来自本次未取得源码的外部依赖；其 `true/false` 参数是否完整等价于
   `simulate`、内部返回值和写入语义均为 **无源码不可判定**，不能把 helper 调用当作安全证据：
   `.../CompactingUpgradeWrapperMixin.java:36-75`。这属于 remainder 风险，不能照搬为 StackUpUp
   的“批处理无余量即成功”先例。任何批处理都必须对每次真实写入记录 offered、stored delta、remainder，并按契约返回，不得写入后补偿。
5. **`require=0` 不能作为容量安全策略。** `ItemStackMixin` 的注入显式 `require = 0`：`.../ItemStackMixin.java:17-30`；配置还将
   `injectors.defaultRequire` 设为 0：`.../biggerstacks.mixins.json:25-27`；仓库内另有 `require=0` 目标未必在配置清单中。对可选兼容
   mod，缺目标可以是明确 skip；对原版/Forge 基础容量路径，注入未命中必须留下可定位失败，而不是静默运行后继续虚报广告。

## 4. StackUpUp 的最佳目标架构

### 4.1 规范目标数据流

```text
.su / .su.md / state / all effective overrides
  → RuleSourceLocator.resolveLoadOrder()
  → RuleReloadPipeline.loadDslRules()
      ├─ Markdown/DSL 分流
      ├─ tokenizer → parser → compiler
      ├─ rule ordering and override merge
      ├─ literal/tag/item validation
      └─ RuntimeContextRequirements provider plan
  → immutable RuleSnapshot(version, hash, rules, overrides, requirements, diagnostics)
  → RuleRuntime.replaceRuntime(snapshot, oreDictIndex)  // atomic
  → StackLimitService.resolve(StackContext)              // cache by snapshot-derived key
  → StackLimitHooks.*                                    // sole gameplay call surface
      ├─ ItemStack / Item baseline
      ├─ Slot / IInventory advertisement with real clamp
      ├─ known handler write path
      ├─ codec / NBT / creative validation
      └─ early or late Mixin; narrow ASM only when admitted
```

当前 StackUpUp 已有这条链的许多实体：`RuleSnapshot.kt:5-15`、`RuleRuntime.kt:6-43`、`StackContextResolver.kt:14-40`、
`StackLimitService.kt:8-40`、`StackLimitHooks.kt:42-73`。这只是当前实现登记，不等于所有门已通过：例如当前协调器仍将 pipeline
返回的 snapshot 交给发布路径，已有文档明确指出含错误报告的旧快照/发布语义尚未闭合（
`docs/StackUpUp-实现与兼容性说明.md:22,167-179`）。

### 4.2 规则快照与运行态

目标 `RuleSnapshot` 不只是已编译规则列表，还应包含：

- 已按确定顺序合并的所有 `.su` / `.su.md` 规则；
- 所有会影响上限的 item/tag/template/preset override；任何客户端可见的 active cap；
- `RuntimeContextRequirements` provider plan 和由字段读取集合机械推导的 cache-key 元数据；
- snapshot `version`、内容 hash、来源文件清单、诊断摘要和协议 schema 版本；
- 可证明的不可变容器（不能把可变 `List` 或外部 map 引用直接暴露给热路径）。

发布流程应是：读取 → 解析 → 编译 → 校验全部有效覆盖 → 生成完整快照 → 通过所有结构门 → 一次 `AtomicReference`
替换。错误路径只留下带来源的报告；不能发布一个包含部分新规则、旧 override 或旧缓存的混合态。

StackUpUp 当前 `RuleRuntime` 的整体刷新服务实例是可借鉴的实现方向：快照或矿辞索引替换时整体刷新 `StackLimitService`
，避免额外版本判断（`RuleRuntime.kt:31-43`）。后续任务仍需补齐快照内容、不可变边界、错误发布策略和 marker/cache
生命周期；这些不是本文已经完成的生产变更。

`state` 不能在目标架构中只写成一个未定义的输入名，必须区分四层语义：

- Markdown 文件中的 `# state` 被 `MarkdownRuleSource` 合并进每个文件的 `RuleGateContext`：
  `src/main/kotlin/io/alexjoest/stackupup/rules/io/MarkdownRuleSource.kt:23-55`；它是 gate 求值输入，不等同于规则动作。
- 持久化层的三态必须保留：`RuleStateService.getState` 在存储不可用时返回 `null`、key 缺失时返回 `false`；`setState`
  的结果只反映底层文件是否真正改变：`src/main/kotlin/io/alexjoest/stackupup/rules/io/RuleStateService.kt:5-32`、
  `RuleStateStore.kt:5-26`。
- `StackUpUp.setState` 将不可用状态记录为诊断，只有文件实际改变才触发 reload：
  `src/main/kotlin/io/alexjoest/stackupup/StackUpUp.kt:156-176`。
- 目标快照应保存有效 state 的版本/hash 或等价诊断，使 gate 输入与规则内容一起可追溯；当前 `RuleSnapshot` 只有 compiled
  rules/requirements，尚未完成该扩展。

当前 reload 仍有一条 live `Item` 遗留路径：`RuleRuntimeCoordinator` 发布运行态后调用
`StackSizeBackupRegistry.restoreAll()`（`RuleRuntimeCoordinator.kt:53-57`），该 registry 会重新执行 `Item#setMaxStackSize`（
`StackSizeBackupRegistry.kt:8-21`）。它必须被明确标为“移除 live Item 业务状态后的过渡 baseline 清理”，或由新的 baseline
机制替代；在迁移决策前不能同时宣称“完全不改 live Item”和“已完成原子快照”。

### 4.3 上下文求值与缓存

- 热路径唯一输入应是当前 `ItemStack`、已核验的原版基线和当前快照要求的 provider plan。
- `StackContextResolver` 只执行 snapshot 已声明的 providers，不按字段名复制一套分支；当前实现方向见
  `StackContextResolver.kt:16-38`。
- `StackLimitService` 顺序执行 compiled rules，结果再限制到 `1..activeMaxStackSize`；当前实现见
  `StackLimitService.kt:15-40`。
- cache key 必须覆盖所有 matcher 读取字段、metadata、item identity 和 base limit；矿辞、material
  等字段的稳定性和失效条件必须由源码/测试证明，不得由注释代替。
- 任何独立 override cache 若仍存在，必须作为快照构建的一部分或带相同 version/hash 的不可变附属物；不能在快照外被 watcher
  或客户端本地文件静默修改。

### 4.4 真实写入准入，而非广告先行

每个容量站点在进入 Mixin/ASM 目标表前，必须完成以下闭环：

1. **查询面**：明确对外广告方法的 owner/name/完整 descriptor、输入参数和原值语义。
2. **写入面**：找到实际 setter、`insertItem(..., false)`、delegate 调用、持久化或实体存储路径；不能只看 `getSlotLimit`、GUI 或
   `==64`。
3. **分类**：按当前决策记录归入自洽、转发、断链；缺源码/缺可重复行为证据独立记为 `无源码不可判定`，不是第四种确定性分类。
4. **数值边界**：广告值不超过真实写入能力；wrapper 广告不能超过 delegate；主动收紧的槽位（例如单件槽）不能因全局上限被抬高。
5. **真实行为**：以 `simulate=false` 的一次真实调用观察 `offered`、before、after、storedDelta、remainder、目标类和 slot；验证
   `storedDelta + remainderCount == offered`。
6. **模拟隔离**：`simulate=true` 只能用于容量探测或规则判断，不能改变状态、不能参与真实守恒告警，也不能为了审计执行第二次真实写入。
7. **失败处置**：无法闭合就维持原容量/安全上限并报告缺口，不新增 wrapper 广告 patch；不在真实写入后回填、重试、补偿。

这正是 StackUp 与 biggerstacks 都没有提供的 Forge 1.12.2 第三方写入安全证明。StackUpUp 的 `SlotLimitMixin`、
`SlotItemHandlerMixin` 和 `Ae2ItemHandlerInsertLimiter` 当前仍有决策记录所列限制（
`docs/StackUpUp-实现与兼容性说明.md:26-46,76-96`），应由 T2/T3/T10/T12/T13 逐项收敛。

### 4.5 Mixin/ASM 分层与容量守恒绑定

**选择顺序：**

1. 目标是原版/Forge 基础类，且 owner、方法和完整 descriptor 明确：使用 early Mixin。
2. 目标是已确认存在的具体模组类，且目标 mod 在加载阶段可判定：使用独立 late Mixin 配置，按 `isModPresent` 和开关 gating。
3. 已由显式 Mixin 接管的类必须在 `FixedCompatTargets` 中让动态 ASM 避让；不能双重 patch。
4. 只有 Mixin 无法表达、目标方法结构和真实写入路径有证据、且生成的字节码可通过 early Java safety 门时，才用窄范围 ASM。

**注入门必须绑定容量证据：**

- `getSlotLimit`/`getInventoryStackLimit` 只改广告值而不接管真实 setter/insert，直接判为断链或保持 `UNKNOWN`，不能因为
  Mixin 成功应用就获准扩大。
- 包裹原调用使用项目批准的 MixinExtras `@WrapOperation`；只修改表达式结果使用 `@ModifyExpressionValue`；不新增 `@Redirect`
  。具体 API、provider、shaded/standalone 关系仍要以当前 MixinBooter 10.7 和构建产物核对，不能使用 DeepWiki 的未来版本示例。
- 静态目标 handler 用 Java `private static`，重载必须写完整 descriptor，例如 `getInventoryStackLimit()I` 与
  `getInventoryStackLimit(I)I` 不能混用。
- 核心 vanilla/Forge 注入不应依赖 `require=0` 静默成功；可选 mod 目标缺失时必须记录 skip，核心目标缺失时 fail-fast
  并阻止产生不受控广告。
- ASM core/early path 保持纯 Java，禁用 Kotlin 集合、lambda、`enum + when`、方法引用和 `use {}`；`transform` 对空
  `basicClass`/`transformedName` 必须安全处理。当前 `CompatibilityLimitPatch` 的 Java/lambda 护栏问题仍在已有文档中登记（
  `docs/StackUpUp-实现与兼容性说明.md:118-130`）。
- Mixin/AP/refmap 的配置完整性必须能从源码类、JSON 清单、loader、descriptor 和生成 refmap 互相核对。`CleanMix` DeepWiki/官方
  README 只能证明“bootstrap、transformer、AP/refmap 是不同层”；不能证明 StackUpUp 当前依赖或 10.7 的精确生命周期。

### 4.6 网络、客户端服务端快照和数量 codec

StackUp 的 magic byte 思路可以保留为底层编码兼容策略：非负 `count` 在 `0..64` 时保持原版单字节，大于 64 或其他越界值进入扩展编码。但
StackUpUp 的协议必须至少包含：

```text
protocolVersion
codecVersion / supported encodings
feature bits (dynamic count, snapshot sync, audit schema ...)
maximum representable count
snapshotVersion + snapshotHash
complete authoritative RuleSnapshot payload
```

建议的最小交互顺序（后续任务规格，不是当前实现）：

```text
client hello(capabilities, protocol, codec)
  → server accept/reject with reason
  → server sends complete snapshot(version, hash, rules, overrides, cap)
  → client validates schema/hash and atomically installs snapshot
  → server sends update(version, hash, complete snapshot) on reload
  → client ACK or disconnect/disable unsupported feature
```

- 服务端是规则权威；客户端本地 `.su`、旧缓存或独立模板文件不能覆盖远端快照。
- 所有影响动态上限的 override 必须随快照发送，不能重复 biggerstacks 的 `RuleSet`/template 分叉。
- 包读写的数量上下界、负数/溢出、空栈和版本不兼容必须 fail-fast 或明确拒绝；不以“magic byte 能读回来”替代端到端验证。
- 网络同步和容量安全是两个门：包能传递大数量不证明目标库存能写入大数量；必须分别有 codec 测试和真实 remainder 守恒测试。

### 4.7 默认关闭的审计层

审计器只接入 StackUpUp 主动投喂调用点，不全局拦截第三方：`simulate=false` 的真实调用进入守恒统计；`simulate=true`
仅可作为同一调用点的原始观察事件，不计算 `balanced`、不触发告警，也不为审计额外执行真实写入。输出机器可读事件：

```text
schemaVersion
callSite
handlerClass
slot
simulate
offered
before
after
storedDelta
remainderCount
balanced              // 仅真实写入填写；模拟事件为 not-applicable
snapshotVersion
```

默认关闭时不能在热路径读取系统属性、构造事件、分配日志对象或改变返回值。审计结果只能回填目标登记表和决策记录，不能自动生成
patch。
