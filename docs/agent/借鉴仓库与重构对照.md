## 1. StackUp：可借鉴的数据流与不可迁移边界

### 1.1 源码数据流（引用式）

- **入口**：`StackUpCore`（`IFMLLoadingPlugin`）注册 `StackUpTransformer`；`MaxStackConstantPatch` 把 `BIPUSH 64` 替换为 `StackUpHelpers.getMaxStackSize()`，另有整方法/helper splice、ItemStack count 与 packet splice、渲染/创造/库存兼容 patch：`C:/dev/mc/_tmp/StackUp/src/main/java/pl/asie/stackup/StackUpCore.java:22-53`、`core/StackUpTransformer.java:154-219`、`core/MaxStackConstantPatch.java:39-69`。
- **生命周期**：`StackUp.preInit()` 读 Configuration 并创建 `config/stackup`；`postInit/register event` 触发 `reload()`；`ScriptHandler` 按自然序递归枚举文件（`script/ScriptHandler.java:38-69`）；`ScriptContext` 逐行/token 匹配整个 Item registry，按 per-Item map 执行 set/add/subtract/multiply/divide，最后 `Item#setMaxStackSize(target)`（`script/ScriptContext.java:137-173`）。

### 1.2 可借鉴点

1. **旧 Forge 入口职责清晰**：`StackUpCore` 只向 FML 注册 transformer，并在 `injectData` 设置 coremod active（`StackUpCore.java:22-53`）；"加载入口只装载、不承载规则业务"可迁移到 `StackUpUpCore`，但 ASM 选择规则不可迁移。
2. **确定性文件顺序**：`ScriptHandler.processDirectory` 用 `TreeSet` 递归（`ScriptHandler.java:48-69`）；借鉴"输入发现顺序显式、可复核"，用 `RuleSourceLocator.resolveLoadOrder()` + 解析/编译流水线，不恢复直接遍历注册表改写 live `Item` 的模型。
3. **重载前恢复旧值**：`StackUp.reload` 先恢复 `oldStackValues` 再处理（`StackUp.java:152-168`）；只借鉴"重载要有明确旧状态处理和报告"，目标是编译新快照、验证后原子替换。
4. **兼容数量编码形状**：`PacketBufferWriterSplice`/`PacketUtilWriterSplice` 对非负数量 `0..64` 保持单字节、超出后 magic byte + int（`PacketBufferWriterSplice.java:36-76`、`PacketUtilWriterSplice.java:28-49`）；思路可借鉴，但须补版本、能力、最大值/编码范围协商；仅复制 magic byte 不是协议兼容证明。
5. **对失败目标记录实际修改结果**：`ScriptContext.applyChanges` 设置后重读并警告目标值未生效（`ScriptContext.java:192-208`）；可迁移"结果必须可观察"，审计不能把警告替换成写入后补偿。

### 1.3 明确不能照搬的部分

1. **全局 `Item` 上限 ≠ 动态 `ItemStack` 规则**：`ScriptContext` 写 `TObjectIntMap<Item>` 后直接 `Item#setMaxStackSize`（`ScriptContext.java:137-173,192-208`），无法表达同一 `Item` 按 metadata/矿辞/material/tab/NBT 的差异化上限，形不成 `StackContext` 缓存键。
2. **解析即时、可变、局部失败**：`ScriptContext.execute` 捕获 `IOException|TokenException` 后 `printStackTrace` 仍继续 `applyChanges`（`ScriptContext.java:54-72`）；不得把部分解析伪装成完整快照，错误须带来源行列 + fail-fast/旧快照策略。
3. **按接口继承关系和类名扩大容量**：`StackUpTransformer` 按 `IInventory`/`IItemHandler`/`Slot` 实现关系和方法名排队 patch（`StackUpTransformer.java:60-116`），不能证明 setter/`insertItem`/remainder/delegate 写入链可承载大堆叠。
4. **`BIPUSH 64` 是常量命中不是容量证明**：`MaxStackConstantPatch` 见 `BIPUSH` 操作数 64 即替换（`MaxStackConstantPatch.java:39-69`）；同一常量可能是协议/显示/单件槽/真实限制，须先登记 owner/name/完整 descriptor/真实写入语义。
5. **整方法 splice 波及面过大**：`spliceClasses` 按方法名替换整段 `MethodNode`、旧方法改名保存（`StackUpTransformer.java:154-219`）；依赖目标结构、继承关系和映射，不能作默认手段；窄 ASM 仅在 Mixin 无法表达且写入证据闭合时兜底。
6. **资源定位两段 split 不能照搬**：`TokenResourceLocation.apply` 仅接受 `split(":")` 长度 2（`TokenResourceLocation.java:31-51`）；1.12.2 `ResourceLocation` path 可含多冒号，须按已核对 grammar/源码处理，不按冒号数猜 meta。
7. **无第三方写入闭环**：core/ASM/packet 路径无 `insertItem` 返回值、`setStackInSlot` 或第三方 wrapper 完整写入证据，不能把兼容类扫描写成容量安全证明。
8. **无握手/能力协商/规则同步证据**：magic byte + int 只说明单个编码器读写对称，不能据此向不同版本/模组栈发扩展数量。
9. **无 tests/CI/自动验收证据**：参考仓库无守恒门测试与自动化矩阵；"能变换字节码"≠真实写入行为测试。

## 2. biggerstacks-Unofficial：可借鉴的数据流与不可迁移边界

### 2.1 源码数据流（引用式）

- **服务端**：`ServerLifecycleHandler` 构造时经 `ConfigLib.readRuleset(RULESET_FILE)` 读取规则并启动 `ConfigFileWatcher`，更新时先替换规则再广播、停服停止 watcher（`C:/dev/mc/_tmp/biggerstacks-Unofficial/src/main/java/portb/biggerstacks/event/ServerLifecycleHandler.java:22-68`）。
- **客户端**：`RulesetSyncTask` 在 configuration/login 阶段发当前 `RuleSet`（`net/RulesetSyncTask.java:20-43`）；handshake/update packet 分别序列化 `RuleSet`（`net/ClientboundRulesHandshakePacket.java:18-49`、`net/ClientboundRulesUpdatePacket.java:17-43`）；`PacketHandler` 安装两种快照（`net/PacketHandler.java:31-63`）。
- **求值**：`ItemMixin`/`ItemStackMixin` → `ItemStackSizeHelper.applyStackSizeToItem` → `TemplateOverrideConfig.resolveOverride(ItemStack)` + `RuleSet.determineStackSizeForItem(ItemProperties + tag accessor)` → clamp → slot/container/handler/compat Mixin 或 TransformerLib/XML 路径 → tooltip/count 显示。

### 2.2 可借鉴点

1. **服务端加载、watcher、广播完整生命周期**：更新先替换规则再广播（`ServerLifecycleHandler.java:22-68`）；可借鉴 watcher 生命周期收口与"更新事件必须显式发布"。
2. **登录握手与运行期更新分开**：`RulesetSyncTask` configuration 阶段发 `RuleSet`（`RulesetSyncTask.java:20-43`），handshake/update 用同一数据形状（`ClientboundRulesHandshakePacket.java:18-49`、`ClientboundRulesUpdatePacket.java:17-43`、`PacketHandler.java:31-63`）；可借鉴"登录前先有规则、更新用同一形状"的协议分层。
3. **以 `ItemStack` 为求值入口**：`ItemStackSizeHelper` 取 registry id、namespace、标签、物品类型、原始基线交给 `RuleSet`（`util/ItemStackSizeHelper.java:31-77,92-100`）；StackUpUp 已有更严格的 `StackContextResolver`/`StackContext`，沿上下文求值，不回全局 `Item`。
4. **模板覆盖提供 item/tag 优先入口**：`TemplateOverrideConfig` 建 item/tag 查找表并 `resolveOverride(ItemStack)`（`config/TemplateOverrideConfig.java:113-181,310-336`）；可借鉴"覆盖规则可枚举、可缓存、可测试"，但有效覆盖须纳入同一权威快照。
5. **按 mod gating 拆分兼容配置**：`biggerstacks.mixins.json` 统一清单 + plugin（`.../biggerstacks.mixins.json:1-27`）；`TransformerEngine.shouldApplyMixin` 按包名提取 mod id 查加载列表（`TransformerEngine.java:111-147`）；late loader 保持每模组独立、按 `isModPresent` 与开关排队。
6. **区分规则传输与能力协议**：`PacketHandler` 注册 `PROTOCOL_VERSION = "1"` 的 configuration/play payload（`PacketHandler.java:20-52`）；可借鉴协议入口，但单字符串版本不足以描述 codec、快照 schema、最大值与客户端能力。

### 2.3 明确不能照搬的部分

1. **`RuleSet` 同步 ≠ 所有有效覆盖同步**：`ItemStackSizeHelper` 先调独立 `TemplateOverrideConfig.resolveOverride` 再查 `StackSizeRules.getRuleSet()`（`ItemStackSizeHelper.java:31-43`）；覆盖文件为规则文件旁的 `biggerstacks-template-overrides.json`，有独立 `ITEM_OVERRIDES`/`TAG_OVERRIDES`（`TemplateOverrideConfig.java:84-181`），handshake/update 只带 `RuleSet` 不带覆盖 → 客户端覆盖可能不同步。**StackUpUp 规定：所有影响上限的规则、模板、tag/item override、preset、active cap 都进入同一权威 `RuleSnapshot` 或可验证快照包**。
2. **客户端本地 fallback 制造权威性分叉**：`ClientEvents.loadRulesetOnLogin` 对远端仍读本地规则、异常置 null（`event/ClientEvents.java:57-79`）；客户端只能用服务端协商验证过的快照，本地文件不得覆盖远端权威。
3. **`scaleSlotLimit` 只按原槽位和全局值缩放**：用 `original`、全局 `getMaxStackSize()`、baseline，特殊处理 `original == 1`，不读当前 `ItemStack`（`util/StackSizeHelper.java:15-45`）；不能证明 item-aware 容量或真实 setter/insert 承载，只能作"显示/传输缩放是独立语义"的反例。
4. **`CompactingUpgradeWrapperMixin` 无真实插入闭环**：直接调 `inventoryHandler.insertItem(resultCopy, false)` 不接收返回值（`mixin/compat/sophisticatedcore/CompactingUpgradeWrapperMixin.java:64-70`）；`InventoryHelper` 来自无源码外部依赖，其 `true/false` 是否等价 `simulate`、返回值和写入语义 **无源码不可判定**（`:36-75`）——remainder 风险，不能照搬为"批处理无余量即成功"；批处理须对每次真实写入记录 offered、stored delta、remainder 并按契约返回，不写入后补偿。
5. **`require=0` 不能作容量安全策略**：`ItemStackMixin` 注入 `require = 0`（`mixin/vanilla/stacksize/ItemStackMixin.java:17-30`），配置 `injectors.defaultRequire=0`（`biggerstacks.mixins.json:25-27`）；可选 mod 缺目标可明确 skip，原版/Forge 基础容量路径注入未命中须留可定位失败。
6. **未列入配置的 Mixin 是加载完整性风险**：清单 `biggerstacks.mixins.json:7-20` 与源码不一致，如 `mixin/vanilla/stacksize/ItemEntityMixin.java:16-29` 不在清单内且注入 `require = 0`（`:22-24`），加载方式未经构建/运行验证，标 UNKNOWN；StackUpUp 须有"源码 Mixin ↔ 配置/loader ↔ refmap"完整性护栏。
7. **私有 ModLauncher 反射不可迁移**：`TransformerEngine` 经 `getPrivateField` 访问 `Launcher`/`LaunchPluginHandler` 私有字段（`TransformerEngine.java:41-58,86-98`）；依赖 NeoForge/ModLauncher 私有结构，不能移植 Forge 1.12.2；core/early path 禁以反射绕过证据缺口。
8. **现代 TransformerLib/XML 不是 ASM 事实源**：`TransformerEngine` 注册 `ILaunchPluginService` 并调 `TransformerLib.handleTransformation`（`TransformerEngine.java:46-83`）；第三方源码未提供，不能判定目标选择、失败策略、写入语义；只能借鉴"compat transformer 独立于 vanilla mixin"的分层意图。
9. **现代版本和 Java 语法不可直接移植**：Java 21、NeoForge payload、`record`、组件 API、`ResourceLocation.fromNamespaceAndPath` 不属于 1.12.2；迁移须重新核对 Java 8、LaunchWrapper、SRG/MCP descriptor 和当前 MixinBooter 11.13 artifact。

## 4. StackUpUp 的最佳目标架构

### 4.1 规范目标数据流

```text
.su / .su.md / state / all effective overrides
  → RuleSourceLocator.resolveLoadOrder() → RuleReloadPipeline.loadDslRules()
      （Markdown/DSL 分流 → tokenizer → parser → compiler → 规则排序与 override 合并
       → 字面量/tag/item 校验 → RuntimeContextRequirements provider plan）
  → immutable RuleSnapshot(version, hash, rules, overrides, requirements, diagnostics)
  → RuleRuntime.replaceRuntime(snapshot, oreDictIndex)   // 原子
  → StackLimitService.resolve(StackContext)               // 按快照派生键缓存
  → StackLimitHooks.*                                     // 游戏唯一调用面
      （ItemStack/Item baseline、Slot/IInventory 真实 clamp 广告、已知 handler 写入路径、
       codec/NBT/creative 校验、early/late Mixin；窄 ASM 仅在准入时用）
```

当前 StackUpUp 已有这条链的许多实体：`RuleSnapshot.kt:5-15`、`RuleRuntime.kt:6-41`、`StackContextResolver.kt:14-40`、`StackLimitService.kt:8-40`、`StackLimitHooks.kt:58-75`——只是实现登记，不等于门已通过：例如协调器仍将 pipeline 返回的 snapshot 交给发布路径，含错误报告的旧快照/发布语义尚未闭合（`docs/StackUpUp-实现与兼容性说明.md:22,167-179`）。

### 4.2 规则快照与运行态

目标 `RuleSnapshot` 应包含：按确定顺序合并的全部 `.su`/`.su.md` 规则；所有影响上限的 item/tag/template/preset override 与客户端可见 active cap；`RuntimeContextRequirements` provider plan 与机械推导的 cache-key 元数据；`version`、内容 hash、来源文件清单、诊断摘要、协议 schema 版本；可证明的不可变容器（不向热路径暴露可变 `List` 或外部 map 引用）。

发布流程：读取 → 解析 → 编译 → 校验全部有效覆盖 → 生成完整快照 → 过全部结构门 → 一次 `AtomicReference` 替换。错误路径只留带来源的报告，不发布部分新规则+旧 override/旧缓存的混合态。当前 `RuleRuntime` 整体刷新服务实例可借鉴（`RuleRuntime.kt:32-40`）；快照内容、不可变边界、错误发布策略、marker/cache 生命周期仍需后续补齐，不是已完成的生产变更。

`state` 须区分四层语义：

- Markdown `# state` 由 `MarkdownRuleSource` 合并进每文件 `RuleGateContext`，是 gate 求值输入、非规则动作：`rules/io/MarkdownRuleSource.kt:23-55`。
- 持久化三态保留：store 不可用 `getState` 返 `null`、key 缺失返 `false`、`setState` 只反映文件是否真正改变：`rules/io/RuleStateService.kt:5-32`、`RuleStateStore.kt:5-26`。
- `StackUpUp.setState` 将不可用状态记为诊断，仅文件实际改变才触发 reload：`StackUpUp.kt:156-176`。
- 目标快照应保存有效 state 的 version/hash 或等价诊断；当前 `RuleSnapshot` 只有 compiled rules/requirements，未完成该扩展。

当前 reload 仍有 live `Item` 遗留：`RuleRuntimeCoordinator` 发布后调 `StackSizeBackupRegistry.restoreAll()`（`RuleRuntimeCoordinator.kt:53-57`），该 registry 重执行 `Item#setMaxStackSize`（`StackSizeBackupRegistry.kt:8-21`）；必须标为"移除 live Item 后的过渡 baseline 清理"或由新 baseline 替代，迁移决策前不得同时宣称"完全不改 live Item"与"已完成原子快照"。

### 4.3 上下文求值与缓存

- 热路径唯一输入：当前 `ItemStack`、已核验原版基线和当前快照要求的 provider plan。`StackContextResolver` 只执行 snapshot 声明的 providers，不按字段名复制分支（`StackContextResolver.kt:16-38`）。
- `StackLimitService` 顺序执行 compiled rules，结果限制 `1..activeMaxStackSize`（`StackLimitService.kt:15-40`）。
- cache key 覆盖所有 matcher 读取字段、metadata、item identity、base limit；矿辞/material 的稳定性和失效条件须源码/测试证明，不由注释代替。
- 独立 override cache 若存在，必须作为快照构建的一部分或带相同 version/hash 的不可变附属物；不能被 watcher 或客户端本地文件在快照外静默修改。

### 4.4 真实写入准入，而非广告先行

容量站点进入 Mixin/ASM 目标表前须闭合：**查询面**——广告方法 owner/name/完整 descriptor、输入参数、原值语义；**写入面**——实际 setter、`insertItem(..., false)`、delegate、持久化/实体存储路径，不看 `getSlotLimit`、GUI 或 `==64`；**分类**——按决策记录归入自洽/转发/断链，缺源码或行为证据独立记为 `无源码不可判定`（不是第四种确定性分类）；**数值边界**——广告 ≤ 真实写入能力，wrapper 广告 ≤ delegate，主动收紧槽位（如单件槽）不因全局上限抬高；**真实行为**——`simulate=false` 一次真实调用观察 offered/before/after/storedDelta/remainder/目标类/slot，验证 `storedDelta + remainderCount == offered`；**模拟隔离**——`simulate=true` 只用于探测或规则判断，不改状态、不参与守恒告警、不为审计二次真实写入；**失败处置**——无法闭合维持原容量/安全上限并报告缺口，不新增 wrapper 广告 patch，不写入后回填/重试/补偿。

这正是 StackUp 与 biggerstacks 都没有提供的 Forge 1.12.2 第三方写入安全证明。`SlotLimitMixin`、`SlotItemHandlerMixin`、`Ae2ItemHandlerInsertLimiter` 当前仍有决策记录所列限制（`docs/StackUpUp-实现与兼容性说明.md:26-46,76-96`），应由 T2/T3/T10/T12/T13 逐项收敛。

### 4.5 Mixin/ASM 分层与容量守恒绑定

**选择顺序：** 原版/Forge 基础类且 owner、方法、完整 descriptor 明确 → early Mixin；已确认存在的具体模组类且加载阶段可判定 → 独立 late Mixin 配置按 `isModPresent` 和开关 gating；已由显式 Mixin 接管的类在 `FixedCompatTargets` 中让动态 ASM 避让，不双重 patch；只有 Mixin 无法表达、目标方法和真实写入路径有证据、且字节码过 early Java safety 门时才用窄 ASM。

**注入门绑定容量证据：**

- `getSlotLimit`/`getInventoryStackLimit` 只改广告而不接管真实 setter/insert → 断链或保持 `UNKNOWN`，不因 Mixin 应用成功获准扩大。
- 包裹原调用用 MixinExtras `@WrapOperation`，只改表达式结果用 `@ModifyExpressionValue`，不新增 `@Redirect`；API/provider/shaded 关系以当前 MixinBooter 11.13 和构建产物核对，不用 DeepWiki 未来版本示例。
- 静态目标 handler 用 Java `private static`，重载写完整 descriptor（`getInventoryStackLimit()I` 与 `getInventoryStackLimit(I)I` 不混用）。
- 核心 vanilla/Forge 注入不依赖 `require=0` 静默成功；可选 mod 缺目标记录 skip，核心目标缺失 fail-fast 并阻止不受控广告。
- ASM core/early path 纯 Java：禁 Kotlin 集合、lambda、`enum+when`、方法引用、`use {}`；`transform` 对空 `basicClass`/`transformedName` 安全处理。`CompatibilityLimitPatch` 的 Java/lambda 护栏问题已登记（`docs/StackUpUp-实现与兼容性说明.md:118-130`）。
- Mixin/AP/refmap 配置完整性须从源码类、JSON 清单、loader、descriptor、生成 refmap 互相核对。CleanMix DeepWiki/官方 README 只能证明"bootstrap、transformer、AP/refmap 是不同层"，不能证明当前 11.13/0.7.1 的精确生命周期。

### 4.6 网络、客户端服务端快照和数量 codec

StackUp 的 magic byte 可保留为底层编码兼容策略（`0..64` 保持原版单字节，越界进扩展编码），但协议至少包含：`protocolVersion`、`codecVersion/supported encodings`、`feature bits`、`maximum representable count`、`snapshotVersion + snapshotHash`、完整权威 `RuleSnapshot` payload。

最小交互顺序（后续任务规格，非当前实现）：

```text
client hello(capabilities, protocol, codec)
  → server accept/reject with reason
  → server sends complete snapshot(version, hash, rules, overrides, cap)
  → client validates schema/hash and atomically installs snapshot
  → server sends update(version, hash, complete snapshot) on reload
  → client ACK or disconnect/disable unsupported feature
```

- 服务端是规则权威；客户端本地 `.su`、旧缓存、独立模板文件不能覆盖远端快照。
- 所有影响动态上限的 override 随快照发送，不重复 biggerstacks 的 `RuleSet`/template 分叉。
- 包读写的数量上下界、负数/溢出、空栈、版本不兼容 fail-fast 或明确拒绝；不以"magic byte 能读回来"替代端到端验证。
- 网络同步与容量安全是两个门：包能传大数量 ≠ 目标库存能写大数量；分别有 codec 测试和真实 remainder 守恒测试。

### 4.7 默认关闭的审计层

审计器只接入 StackUpUp 主动投喂调用点，不全局拦截第三方：`simulate=false` 真实调用进守恒统计；`simulate=true` 仅作同一调用点原始观察事件，不计算 `balanced`、不告警、不为审计额外真实写入。事件字段：`schemaVersion / callSite / handlerClass / slot / simulate / offered / before / after / storedDelta / remainderCount / balanced（仅真实写入填写；模拟为 not-applicable）/ snapshotVersion`。

默认关闭时热路径不读系统属性、不构造事件、不分配日志对象、不改返回值。审计结果只回填目标登记表和决策记录，不自动生成 patch。
