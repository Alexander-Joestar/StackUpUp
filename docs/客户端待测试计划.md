## 1. 测试环境与启动

### 1.1 普通开发客户端

- Minecraft 1.12.2、Forge 14.23.5.2847。
- 使用当前项目构建基线：MixinBooter 11.17、CleanMix 0.7.2、`IMixinConnector`；不要用旧 10.7/旧 loader 的结论替代当前结果。
- 目标模组必须记录 **实际文件名、版本、mod id**。第三方 jar/源码缺失时，静态结论保持“无源码不可判定”，不能按类名猜测。
- 从项目根目录启动：

```bat
.\gradlew.bat runClient
```

- 可选开发辅助（只做目标物品发放和观察，不是完整门禁）：

```bat
.\gradlew.bat runClientAutoTest
```

- `runClientAutoTest` 只会进入测试世界、注入临时规则、执行 `/give` 并观察玩家背包；不会代替人工打开容器、点击槽位、操作网络或验证第三方写入。规则注入/目标缺失时客户端驱动只
  `abort`，没有可靠的进程失败码。
- 每轮测试使用新世界或清空并记录初始状态。规则文件通常为运行目录下 `config/stackupup/main.su`；直接改文件后执行：

```text
/stackupup reload
```

- 配置项 `general.maxStackSize` 是全局兼容上限；`compat.vanilla.craftingSlotLimit` 是工作台网格和合成结果槽的独立上限，默认
  64。`0` 保持原版/默认行为，大于 `0` 使用自定义值；它主要影响批量合成性能，不是平衡设置。NuclearCraft 的升级上限位于
  `compat.nuclearcraft.speedUpgradeLimit` / `energyUpgradeLimit`，默认 `0` 表示保持 NuclearCraft 默认值 64。改配置后通过 StackUpUp 配置界面保存，或重启客户端确认配置已生效；也可执行 `/stackupup reload`，不要把 F3+T 当作配置重载。

## 2. 统一操作、边界和记录

### 2.1 前置数据

- 先用未加规则的物品作基线，确认原版通常上限为 64；另保留一个未加规则物品作对照。
- 推荐分档：`64`、`65`、`128`、`512`、`1024`，另测 `上限 + 1`（例如 1025）。
- 推荐规则示例（按实际可获得物品替换）：

```su
item = minecraft:stone -> 128
item = minecraft:iron_ingot -> 1024
```

- 规则命中后核对 `ItemStack` 实际数量、`maxStackSize`、槽位可见上限和容器重新打开后的数量；物品本身上限、配方限制或特殊槽位限制可以进一步收紧，但不能出现广告大于真实写入容量。

### 2.2 每项必做动作

- [ ] 空手放入、拿出、单击取半、右键放一个、拖拽、 shift-click；能自动化的目标再测漏斗/管道/总线投喂。
- [ ] 在目标数量低于上限、等于上限、超过上限时各测一次。
- [ ] 关闭并重新打开 GUI；退出世界再进入；必要时完全重启客户端，核对数量和 NBT 未变化。
- [ ] 记录客户端显示与服务端权威数量是否一致；特别记录“客户端看见有、实际取不出”“点击后回弹”“重登后变化”。
- [ ] 任何一次真实写入都只观察结果，不回填、重试或手工补偿后再判定。

每个场景单独一行或一张表，至少填写：

- `PASS` 只表示该条在指定环境、指定路径实际复现且证据完整；不能外推到同模组其他版本或其他写入路径。
